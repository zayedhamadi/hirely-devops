============================================================
HIRELY - GUIDE DES COMMANDES K3S / KUBECTL
Cluster : vmonee (control-plane) + vmtwo (agent)
Namespace applicatif : hirely
============================================================

CONVENTIONS
- Les commandes supposent que k3s est installé sur vmonee.
- `k` est un alias facultatif. Pour éviter les problèmes d'alias,
  les exemples utilisent `sudo k3s kubectl` ou `kubectl` si configuré.
- Sur vmonee, `sudo k3s kubectl` fonctionne même si kubeconfig n'est
  pas configuré pour l'utilisateur.
- Dans les commandes interactives, quitter avec exit.

------------------------------------------------------------
1. VÉRIFIER K3S ET KUBERNETES
------------------------------------------------------------
sudo systemctl status k3s --no-pager
sudo systemctl is-active k3s
sudo systemctl restart k3s
sudo journalctl -u k3s -n 100 --no-pager
sudo journalctl -u k3s -f
sudo k3s --version
sudo k3s kubectl version
sudo k3s kubectl cluster-info
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get componentstatuses

Alias temporaire pour la session courante :
alias k='sudo k3s kubectl'
k get nodes -o wide

Kubeconfig utilisateur (vmonee) :
mkdir -p ~/.kube
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown "$USER":"$USER" ~/.kube/config
chmod 600 ~/.kube/config
export KUBECONFIG=~/.kube/config
kubectl get nodes -o wide

ATTENTION : après changement de configuration/réseau, vérifier le
kubeconfig et l'adresse du serveur avant de conclure à une panne.

7. EXEC DANS MYSQL - POD DYNAMIQUE
------------------------------------------------------------
# Ouvre un shell MySQL directement, en détectant le pod via son label.
# Le nom peut changer après un rollout/restart : pas besoin de le copier.
POD=$(sudo k3s kubectl get pods -n hirely -l app=mysql -o jsonpath='{.items[0].metadata.name}') && echo "Pod MySQL: $POD" && sudo k3s kubectl exec -it -n hirely "$POD" -- sh

# Depuis le shell du conteneur, ouvrir le client MySQL :
mysql -u root -p

# Ou directement depuis vmonee, sans ouvrir un shell intermédiaire :
POD=$(sudo k3s kubectl get pods -n hirely -l app=mysql -o jsonpath='{.items[0].metadata.name}') && sudo k3s kubectl exec -it -n hirely "$POD" -- mysql -u root -p

# Commandes SQL à exécuter dans le client MySQL :
SHOW DATABASES;
USE nom_base;
SHOW TABLES;
SELECT NOW();
EXIT;

# Voir les variables de l'environnement (attention : peut exposer des secrets)
# À éviter dans un terminal partagé ou une capture d'écran.
# sudo k3s kubectl exec -n hirely "$POD" -- printenv

8. EXEC DANS MONGODB - POD DYNAMIQUE
------------------------------------------------------------
# Ouvre un shell dans le pod MongoDB en détectant son nom actuel.
POD=$(sudo k3s kubectl get pods -n hirely -l app=mongodb -o jsonpath='{.items[0].metadata.name}') && echo "Pod MongoDB: $POD" && sudo k3s kubectl exec -it -n hirely "$POD" -- sh

# Depuis le shell du conteneur :
mongosh

# Ou directement ouvrir mongosh depuis vmonee :
POD=$(sudo k3s kubectl get pods -n hirely -l app=mongodb -o jsonpath='{.items[0].metadata.name}') && sudo k3s kubectl exec -it -n hirely "$POD" -- mongosh

# Commandes MongoDB dans mongosh :
show dbs
use nom_base
db.getCollectionNames()
db.nom_collection.find().limit(5)
exit

# Si l'image exige une authentification, utiliser les identifiants prévus
# dans les Secrets/configurations de ton déploiement. Ne pas les publier.

9. EXEC GÉNÉRIQUE - POD DYNAMIQUE PAR LABEL
------------------------------------------------------------
# Exemple pour n'importe quel workload avec le label app=<application>
POD=$(sudo k3s kubectl get pods -n hirely -l app=<application> -o jsonpath='{.items[0].metadata.name}') && echo "$POD" && sudo k3s kubectl exec -it -n hirely "$POD" -- sh

# Si le conteneur contient bash :
sudo k3s kubectl exec -it <nom-pod> -n hirely -- bash

# Si plusieurs conteneurs sont dans le pod, préciser le conteneur :
sudo k3s kubectl exec -it <nom-pod> -n hirely -c <nom-conteneur> -- sh

------------------------------------------------------------
10. REDÉMARRER / ROLLOUT / SCALE
------------------------------------------------------------
# Redémarrer un Deployment (Kubernetes recrée ses pods)
sudo k3s kubectl rollout restart deployment/<deployment> -n hirely
sudo k3s kubectl rollout status deployment/<deployment> -n hirely
sudo k3s kubectl rollout history deployment/<deployment> -n hirely

# Exemples
sudo k3s kubectl rollout restart deployment/discovery-service -n hirely
sudo k3s kubectl rollout restart deployment/gateway -n hirely
sudo k3s kubectl rollout status deployment/gateway -n hirely

# Modifier le nombre de replicas (attention aux bases de données stateful)
sudo k3s kubectl scale deployment/<deployment> --replicas=2 -n hirely
sudo k3s kubectl scale deployment/<deployment> --replicas=1 -n hirely

# Annuler le dernier rollout si possible
sudo k3s kubectl rollout undo deployment/<deployment> -n hirely

ATTENTION : éviter de scaler MySQL/MongoDB à plusieurs replicas sans
architecture de réplication adaptée. Ne pas supprimer les PVC/PV à l'aveugle.

# 1) vérifier le namespace et le nom exact
# 2) vérifier l'état des PVC/PV
# 3) vérifier qu'une sauvegarde restaurable existe
# 4) ne jamais afficher/committer les Secrets ou fichiers .env

------------------------------------------------------------
17. RAPPELS IMPORTANTS
------------------------------------------------------------
- `get` : afficher les ressources.
- `describe` : détails + événements d'une ressource.
- `logs` : journaux d'un conteneur.
- `exec` : exécuter une commande dans un conteneur.
- `rollout restart` : redémarrer proprement un Deployment.
- Le nom du pod change souvent ; privilégier Deployment ou label app.
- Les commandes MySQL/Mongo ci-dessus choisissent le premier pod
  correspondant au label. Elles supposent qu'un pod correspondant existe.
- Ne pas partager les mots de passe, tokens JWT, Secrets ou backend.env.
